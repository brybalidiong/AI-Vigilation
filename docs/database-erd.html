Application tables — accounts_* (13 tables)

Table Function Relationships Who uses it Notes
accounts_userprofile Extends login with role (admin / instructor / student), institute, enrollment status, and Google profile photo URL. 1:1 with auth_user All roles Created during admin registration or first Google login; drives access control in the API. Legacy accounts may have no institute until an admin assigns one.
accounts_subject Represents a course: name, code, announcements, and optional display photo. Many → auth_user (instructor); parent of rosters, enrollments, exams Instructor, Student Unique (instructor, code). Photo path stored in Supabase Storage.
accounts_studentset Named roster or class section (e.g. “BSIT 3A”) under a subject. → accounts_subject, → auth_user (created_by) Instructor Instructor creates rosters to group students for exam assignment.
accounts_enrolledstudent Lists student emails allowed in a specific roster. → accounts_studentset Instructor, Student Unique (email, student_set). Used to validate who may take assigned exams.
accounts_subjectenrollment Links student emails to a subject (course-level enrollment). → accounts_subject Instructor, Student Unique (subject, email). Determines which courses appear on the student dashboard.
accounts_examset Exam or assignment: title, schedule, PDF/file, time limit, max attempts, final flag. → accounts_subject; M2M ↔ accounts_studentset via join table Instructor, Student exam_file is a Storage path. is_final locks questions after publish.
accounts_examset_assigned_sets Join table: which rosters may access which exam. ↔ accounts_examset + accounts_studentset Instructor If empty, exam may be open to all rosters in the subject (per app logic).
accounts_examsubmission One student’s attempt on an exam: score, integrity %, start/submit times, proctoring flags. → accounts_examset; parent of proctoring logs & reports Student, Instructor Unique (exam_set, student_email). Tracks tab_switches, terminated, attempt_count.
accounts_examquestion Individual question: multiple choice or identification, choices (JSON), correct answer. → accounts_examset Instructor, Student Ordered by order. MC auto-graded; identification graded manually.
accounts_studentanswer Student’s answer to one question, with optional auto-grade result. → accounts_examset, → accounts_examquestion Student, Instructor Unique (exam_set, question, student_email). is_correct null for identification.
accounts_examproctoringevent Timestamped action log during an exam (tab switch, copy, split screen, exam start/end, etc.). → accounts_examsubmission; optional link from evidence Student (writes), Instructor (reads) Severity: info / warning / critical. Used to compute integrity score and audit trail.
accounts_examproctoringevidence Webcam or screen capture stored as image proof of exam session. → accounts_examsubmission; optional → accounts_examproctoringevent Student (uploads), Instructor (views) Images in Supabase Storage (proctoring_evidence/). Periodic + event-triggered snapshots.
accounts_examintegrityreport Generated summary per attempt: integrity %, event/evidence counts, narrative text. → accounts_examsubmission Instructor Unique (submission, attempt_number). Built on exam submit; shown in integrity report UI.

Authentication tables — auth_* (6 tables)

Table Function Relationships Who uses it Notes
auth_user Django user accounts: username, email, password hash, staff/superuser flags. 1:1 accounts_userprofile; referenced by subjects & rosters All roles Primary login table. The admin username and password hash live here in Supabase PostgreSQL; Google users also have Django accounts.
auth_group Named permission groups (e.g. “Moderators”). M2M with users and permissions Django Admin Framework table; not used directly by the Vue frontend today.
auth_permission Granular permissions (add/change/delete per model). Linked to groups and users Django Admin Auto-created for each model; supports Django Admin access control.
auth_user_groups Join table: which groups a user belongs to. ↔ auth_user + auth_group Django Admin Many-to-many link table.
auth_user_user_permissions Extra permissions assigned directly to a user (outside groups). ↔ auth_user + auth_permission Django Admin Overrides or supplements group permissions.
auth_group_permissions Permissions granted to a group. ↔ auth_group + auth_permission Django Admin Defines what members of a group can do in Admin.

Django framework tables — django_* (4 tables)

Table Function Relationships Who uses it Notes
django_migrations Records which database migrations have been applied. None (standalone) Django (system) Updated by python manage.py migrate. Do not edit manually.
django_session Server-side session data for logged-in browser sessions. Keyed by session id Django (system) Used if session middleware is active; API primarily uses JWT instead.
django_content_type Maps each model to an ID for the permission framework. Referenced by auth_permission Django (system) Auto-maintained when models are registered.
django_admin_log Audit log of actions performed in Django Admin (who changed what). → auth_user, content types Django Admin Stores add/change/delete history for admin UI actions.

Data flow summary

  1. Instructor creates subject → rosters → enrolls students → creates exam and questions.
  2. Student opens exam → submission starts → proctoring events and evidence are recorded.
  3. On submit → answers saved → integrity report generated → instructor reviews report in Exam Progress.
  4. auth_* and django_* tables support login, permissions, and framework operation in the background.
